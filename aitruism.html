Core thesis

A three-layer locus of control

Each layer sees something the others cannot, and each stops something the others cannot. Together they close the gaps a single guardrail leaves open.

Layer 1 · Perimeter

LLM Gateway

The front-door guard

  • PII detection and redaction
  • Prompt-injection screening
  • Cost control and caching
  • Content moderation

Layer 2 · Introspection

OTEL Sidecar

The surveillance

  • Hallucination detection
  • Topic drift and goal hijacking
  • Cross-session leakage
  • Stateful, asynchronous analysis

Layer 3 · Action

MCP Tool Layer

The vault door

  • Synchronous policy check before any damaging action
  • Open Policy Agent decision on every call
  • Cannot be bypassed by the model or the agent

Every capability is scored 0 to 100 per layer, with a written rationale. That matrix, not any single component, is the intellectual core of AiTruism: it tells you where a control belongs and why.

What it covers

Built on the open-source guardrail ecosystem

AiTruism composes proven scanners and adds the placement, prioritization and analytics that make them enforceable in production.

Scanner catalog

Thirteen gateway scanners, four priorities

  1. 1Alignment
  2. 2Data disclosure
  3. 3Unreasonable behavior
  4. 4Trivial correctness

Each scanner is classed algorithmic or model-based and linked to its upstream project, so you know its cost, latency and failure mode before you switch it on.

built on LlamaFirewall · Presidio · Guardrails Hub · NeMo · Semgrep

Custom business scanners

Your rules, three ways

  1. Regex
  2. Semantic embedding search
  3. Judge LLM

From cheap and exact to expensive and nuanced, with explicit trade-offs and one placement rule: fast and stateless at the gateway, context-heavy in the sidecar.

Sidecar internals

A seven-step analysis pipeline

Ingest over gRPC, batch, orchestrate in a Go processor, dispatch asynchronously to Python analysis services, enrich each span with a validation.score, and export to SigNoz or Jaeger. eBPF adds kernel-level visibility into code nothing else instruments.

Analytics

Deviation and bias detection on real traces

Business metrics are identified automatically from OTEL traces, then watched for temporal deviation (monotonic trends, period changes, spikes) and bias (protected attributes, disparity ratios, Cohen's d, intersectional effects). Runs interactively or as a batch scanner that emits pass and fail counts for CI.

Adoption

Four phases, value from the first

The control plane is adopted incrementally. Each phase is useful on its own and prepares the next.

Phase 1 · 1 to 2 months

Gateway and OTEL baseline

Perimeter enforcement and full tracing of every model call.

Phase 2 · 2 to 3 months

Sidecar with hallucination detection

Deep asynchronous analysis on top of the traces you already collect.

Phase 3 · ongoing

Dynamic policy enforcement

Policies evolve with what the sidecar learns, enforced at the tool layer.

Phase 4 · enterprise

Hardening

OPA or Cedar policies, Vault PII tokenization, Kafka to SIEM, service-mesh enforcement, embedded Judge LLMs.
